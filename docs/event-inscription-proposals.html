Notas de implementación

apiPOST /events/:id/join con body: { message?: string }. Si requiresApproval=true → status=pending; si false → status=approved.
apiGET /events/:id/participants?status=pending → lista de solicitudes para el organizador.
apiPATCH /events/:id/participants/:userId con body: { status: 'approved' | 'rejected' }. Solo el organizador puede llamar este endpoint.
notificationsAl aprobar/rechazar → notificación push al participante. Al llegar nueva solicitud → notificación al organizador.
badgeEl ícono de "Eventos" en el bottom nav muestra un badge con el número de solicitudes pendientes para el organizador.

Notas de implementación

routeGET /e/:shareToken → endpoint público (sin JWT). Devuelve detalles del evento si el token es válido. La ruta /e/:token ya está en el plan de rutas Angular.
redirectAl hacer clic en "Iniciar sesión para inscribirme", guardar el shareToken en sessionStorage. Post-login, verificar si existe y redirigir de vuelta al evento.
joinMisma lógica que Flujo A/B: POST /events/:id/join. La diferencia es que el usuario llegó por link privado, no desde el feed.
qr_codeLa variante QR usa la misma URL del shareToken. El QR es generado client-side (ya existe qrDataUrl() en el perfil) con la URL completa del evento.

Recomendación de implementación Los tres flujos usan el mismo endpoint POST /events/:id/join. El backend ramifica según requiresApproval y la comparación de participant count vs maxParticipants. El frontend maneja los estados con una sola señal participationStatus: 'none' | 'approved' | 'pending' | 'waiting' | 'rejected' que determina qué UI se muestra. Prioridad de implementación: Flujo A → Flujo B → Flujo C.
